# 启发式排程生产级重构技术方案

## 1. 目标与边界

本方案重构 `Services/Heuristics/HeuristicScheduler.cs`，使启发式排程能够作为 CP-SAT 的可行 Hint，并在受控降级模式下产出可验证的排程结果。

必须处理以下交错现场数据：

- 固定工单：已下发、调机、生产中、暂停等不可移动工单；可在优化起点前、跨越起点或未来发生。
- 异常窗口：设备或模具不可用；多个窗口可重叠、嵌套或相接。
- 模具-设备组合：只能从 `Job.ProductionAlternatives` 选择合法 `(MoldId, MachineId, DurationMinutes)`。
- 换模时间：同设备相邻生产工单的模具不同，必须占用该设备的准备时间。
- 颜色顺序：相邻生产工单必须满足 `ColorSequencePolicy.IsAllowed`。
- 设备与模具互斥：生产、准备和异常/固定占用均不得重叠。

不在本次启发式重构中处理的业务包括拆单、人员/物料资源、跨班次日历、软约束权重调参；但内部抽象必须允许后续扩展资源类型。

## 2. 不可变生产约束

任意返回为 `IsFeasible=true` 的启发式结果必须满足：

1. 每个已排动态工单恰好选择一个 `ProductionAlternative`。
2. 输出的 `(ProductId, MoldId, MachineId)` 必须属于输入的有效 MPD 关系。
3. 同一设备上生产、换模准备、固定工单和设备异常两两不重叠。
4. 同一模具上生产、固定工单和模具异常两两不重叠。
5. 动态工单开始时间不早于 `OptimizationCutoffMinutes`，结束时间不超过统一 Horizon。
6. 同设备相邻生产工单的颜色方向合法；不同模具时，准备时间完整且占用设备。
7. 固定工单的设备、模具、开始和结束时间不可被启发式修改。
8. 未排工单必须显式返回原因；不得使用部分结果伪装为完整可行结果。

## 3. 现有实现的替换原则

删除“先分配设备 -> 按设备串行排程 -> 事后顺延”的流程。禁止通过简单将工单开始时间推后修复冲突，因为推后会改变其与前后工单的换模和颜色关系。

替换为：

```text
规范化固定/异常占用
    -> 初始化设备和模具资源日历
    -> 枚举合法 Alternative 的可行插入位置
    -> MRV + regret-2 选择工单和位置
    -> 原子更新日历
    -> 有界局部修复
    -> 独立可行性验证
```

## 4. 数据模型设计

新增以下 internal 类型，建议放在 `Services/Heuristics/Calendar`。

```csharp
internal enum CalendarEntryKind
{
    Production,
    Setup,
    FixedProduction,
    Blocked
}

internal sealed record CalendarEntry(
    int StartMinutes,
    int EndMinutes,
    CalendarEntryKind Kind,
    string SourceId,
    Job? Job,
    ScheduledOperation? Operation);

internal sealed record SetupReservation(
    string MachineId,
    int StartMinutes,
    int EndMinutes,
    string PreviousOperationId,
    string NextOperationId);

internal sealed record InsertionCandidate(
    Job SourceJob,
    ProductionAlternative Alternative,
    int SetupBeforeMinutes,
    int ProductionStartMinutes,
    int ProductionEndMinutes,
    int SetupAfterMinutes,
    int IncrementalTardiness,
    int IncrementalSetupCost,
    int IncrementalColorCost,
    int TotalCost);

internal sealed record HeuristicUnscheduledJob(
    string OrderChildNo,
    string Reason,
    IReadOnlyList<string> RejectedAlternatives);

internal sealed record HeuristicBuildResult(
    IReadOnlyList<ScheduledOperation> Operations,
    IReadOnlyList<HeuristicUnscheduledJob> UnscheduledJobs,
    bool IsFeasible,
    string Status,
    double ObjectiveValue);
```

`ScheduleResult` 可以保持不变以减少接口改动，但 `HeuristicBuildResult` 应作为内部真实返回模型。只有 `IsFeasible=true` 才转换为完整 `ScheduleResult` 并作为 CP-SAT Hint；否则只保留已排部分用于诊断，不能作为生产回退计划。

### 4.1 资源日历

实现两个相同接口的日历实例：`MachineCalendar` 与 `MoldCalendar`。

```csharp
internal interface IResourceCalendar
{
    IReadOnlyList<CalendarEntry> Entries { get; }
    IReadOnlyList<TimeWindow> FindFreeWindows(int start, int end, int requiredMinutes);
    bool IsFree(int start, int end);
    CalendarCheckpoint CreateCheckpoint();
    void Restore(CalendarCheckpoint checkpoint);
    void Add(CalendarEntry entry);
    void RemoveBySourceId(string sourceId);
}
```

要求：

- 每个日历内部最终保存按开始时间排序、互不重叠的占用区间。
- 异常窗口先按资源执行 `TimeWindowUtils.Merge`，再写入 `Blocked` 条目；重叠窗口的来源 ID 需保留在诊断信息中。
- 固定工单不能静默合并。若同设备或同模具的固定工单互相重叠，预处理或日历初始化必须返回 `InvalidFixedSchedule`。
- `Setup` 是设备日历中的显式占用；模具日历不占用 Setup。
- 日历添加必须是原子的：设备生产、模具生产和相关 Setup 任一失败时全部回滚。

推荐首版使用按开始时间排序的 `List<CalendarEntry>` 加二分查找；在单资源条目超过 2,000 时再替换为 interval tree。不要每次插入后对整个列表做全量 `Sort`。

## 5. 固定单、异常和准备时间的时间语义

### 5.1 固定工单

每个固定工单初始化为：

- 设备日历：`FixedProduction`，区间为 `[StartMinutes, EndMinutes)`。
- 模具日历：`FixedProduction`，区间相同。
- 生产序列上下文：保留 `Job`，使动态工单可校验 `固定 -> 动态` 与 `动态 -> 固定` 的颜色和换模。

固定单在优化起点之前结束时，仍是其后首个动态单的颜色/换模前序；固定单在未来时，动态工单只能插在其前、后或两个固定单之间的合法空档。

### 5.2 异常窗口

异常是 `Blocked`，没有颜色和模具上下文，但不会重置生产序列。举例：

```text
固定单 A -> 设备异常 -> 动态单 B
```

`B` 的前序生产工单仍是 `A`。如果 A 与 B 模具不同，A->B 的 Setup 必须放置在异常结束后的可用设备空档内，并在 B 开始前完成；不能因异常条目位于中间而跳过颜色/换模检查。

### 5.3 Setup 的显式预留

对设备生产序列中的相邻生产节点 `P -> C`：

```text
setup = SetupCalculator.Compute(P.Job, C.Job, config)
setup interval = [C.StartMinutes - setup, C.StartMinutes)
```

要求该 Setup 区间完全位于设备空闲窗口内，不得与生产、固定单或异常重叠。插入 `C` 到 `P -> N` 时，必须原子执行：

1. 删除旧的 `P -> N` Setup（若存在）。
2. 验证颜色 `P -> C`、`C -> N`。
3. 预留 `P -> C` 与 `C -> N` 的 Setup。
4. 插入 C 的设备生产、模具生产节点。
5. 任一步失败则回滚到插入前状态。

## 6. 可行插入位置枚举

为一个 `Job` 的每个 `ProductionAlternative` 枚举候选插入位置，禁止只在设备尾部追加。

### 6.1 Slot 定义

设备 Slot 由设备生产序列的相邻生产节点定义：

```text
left production (可为空) -> 可用窗口集合 -> right production (可为空)
```

异常和固定单将时间轴切分为多个可用窗口，但 Slot 的 `left/right production` 必须跨越异常持续追溯最近的生产节点。

### 6.2 单个候选的判定步骤

给定 Job `J`、Alternative `A(MoldId, MachineId, Duration)`、Slot `(P, N)`：

1. 若 `P` 存在且 `!ColorPolicy.IsAllowed(P, J[A])`，拒绝。
2. 若 `N` 存在且 `!ColorPolicy.IsAllowed(J[A], N)`，拒绝。
3. 计算 `setupBefore = Setup(P, J[A])`、`setupAfter = Setup(J[A], N)`。
4. 从设备日历查询可容纳 `setupBefore + duration + setupAfter` 的空闲窗口；首单没有 `setupBefore`，尾单没有 `setupAfter`。
5. 在窗口内选择最早生产开始时间 `productionStart = windowStart + setupBefore`。
6. 对模具日历查询 `[productionStart, productionStart + duration)` 是否空闲；若冲突，移动到下一模具空档并重新验证设备窗口和 Setup。
7. 验证 `productionEnd <= HorizonEndMinutes`，并计算拖期、换模、颜色和完工成本。
8. 返回 `InsertionCandidate`；所有条件均满足才视为可行。

候选排序使用确定性规则：

```text
TotalCost
-> IncrementalTardiness
-> ProductionEndMinutes
-> MachineId ordinal
-> MoldId ordinal
```

## 7. 工单选择和构造算法

### 7.1 工单优先级

每轮对剩余工单生成候选列表，按以下顺序选择下一个工单：

1. 候选数为 0 的工单进入局部修复，不直接忽略。
2. MRV：候选数最少优先。
3. regret-2：次优候选成本减最优候选成本，差值最大优先。
4. 交期最早优先。
5. `OrderChildNo` 字典序，确保输入顺序不同不会导致随机计划。

`regret-2` 不是候选数量；只有至少两个候选时才有意义，无第二候选时赋为最大值。

### 7.2 伪代码

```text
calendars = BuildCalendars(fixedOperations, mergedAbnormalWindows)
remaining = all dynamic jobs
scheduled = []

while remaining is not empty:
    choices = remaining.map(job => EnumerateFeasibleInsertions(job, calendars))
    if every choices is empty:
        if not TryBoundedRepair(remaining, scheduled, calendars):
            break
        continue

    job = SelectByMrvRegretDueDate(choices)
    candidate = LowestCost(job.candidates)
    CommitAtomically(candidate, calendars)
    scheduled.add(candidate.operation)
    remaining.remove(job)

validation = ValidateHeuristicSchedule(problem, scheduled, remaining)
return BuildResult(scheduled, remaining, validation)
```

## 8. 有界局部修复

局部修复的目的是避免一次贪心选择导致“有可行解却漏排”，但必须有严格资源预算。

### 8.1 Ejection Chain

当关键工单无可行位置时：

1. 在其候选设备/模具相关的动态工单中，选择最多 3 个“移出代价最低”的工单。
2. 建立日历 checkpoint，移出这些动态工单及其 Setup。
3. 插入关键工单。
4. 按 MRV + regret-2 重新插入被移出的工单。
5. 成功则提交 checkpoint；失败则恢复 checkpoint 并尝试下一个组合。

限制：

```text
最大移出深度：3
每个失败工单最多尝试：20 个移出组合
总修复尝试：min(100, 动态工单数 * 2)
修复时间预算：启发式总预算的 30%
```

不得移出固定工单、异常窗口或已明确锁定的工单。

### 8.2 多次确定性构造

若第一次构造未全覆盖，可最多执行 3 次构造：

- 第 1 次：MRV + regret-2 + 最低成本。
- 第 2 次：MRV + 交期优先。
- 第 3 次：MRV + 换模最少优先。

保留“覆盖工单最多，其次业务目标最低”的已验证结果。禁止使用未校验的随机结果；如需随机打破完全相同的 tie，随机种子必须由 `RequestId` 或输入哈希确定，并记录到日志。

## 9. 独立可行性校验器

新增 `HeuristicScheduleValidator`，不复用调度器内部状态，以防同一逻辑同时存在构造和校验错误。

```csharp
internal interface IHeuristicScheduleValidator
{
    HeuristicValidationResult Validate(
        SchedulingProblem problem,
        IReadOnlyList<ScheduledOperation> dynamicOperations,
        IReadOnlyList<HeuristicUnscheduledJob> unscheduledJobs);
}
```

校验项：

- 工单覆盖、唯一性、Alternative 合法性。
- 动态工单与固定工单、异常窗口的设备/模具互斥。
- 动态工单之间的设备/模具互斥。
- 每台设备生产序列的颜色方向与 Setup 区间。
- 固定工单前后动态工单的颜色方向与 Setup 区间。
- 起点、Horizon、开始小于结束、拖期计算和输出字段一致性。

校验失败时必须返回结构化错误：`ConstraintType`、资源 ID、时间区间、涉及工单 ID、诊断消息。`IsFeasible=false` 的结果不得作为 CP-SAT Hint 或自动下发计划。

## 10. 与 SchedulingEngine 的集成契约

调整排程引擎语义：

| 场景 | 启发式用途 | 是否可作为最终计划 |
| --- | --- | --- |
| 启发式完整且校验通过 | CP-SAT Hint | 是，受业务降级开关控制 |
| 启发式部分覆盖或校验失败 | 仅诊断 | 否 |
| CP-SAT Optimal/Feasible 且最终校验通过 | 最终计划 | 是 |
| CP-SAT 无解/超时，启发式完整且校验通过 | 受控回退 | 仅在显式降级开关开启时 |
| CP-SAT 无解/超时，启发式不完整或校验失败 | 失败/人工处理 | 否 |

不要再以 `Operations.Count == Jobs.Count` 作为唯一可用判断；必须同时检查状态和校验器结果。

## 11. 建议文件拆分和编码顺序

1. `Services/Heuristics/Calendar/CalendarEntry.cs`：日历条目、类型、checkpoint。
2. `Services/Heuristics/Calendar/ResourceCalendar.cs`：有序占用、合并异常、二分查询、回滚。
3. `Services/Heuristics/Calendar/MachineProductionSequence.cs`：生产前后继、Setup 预留与 Slot 枚举。
4. `Services/Heuristics/HeuristicInsertionEvaluator.cs`：给定 Job/Alternative 枚举 `InsertionCandidate`，不修改日历。
5. `Services/Heuristics/HeuristicScheduler.cs`：选择策略、提交、重启和局部修复编排。
6. `Services/Heuristics/HeuristicScheduleValidator.cs`：独立校验。
7. `Services/SchedulingEngine.cs`：按第 10 节处理 Hint、回退和发布状态。

每个步骤完成后先增加测试，再进入下一步；不要在一个大提交中同时修改预处理、CP-SAT、启发式与 API。

## 12. 测试门禁

必须新增并通过以下用例：

1. 同一模具多设备、同一设备多模具的 Alternative 选择，输出组合必须存在于 MPD。
2. 两个重叠设备异常窗口、嵌套异常窗口和相接异常窗口，动态单不得落入任一区间。
3. 固定单结束于起点前 1 分钟，首个动态单必须保留颜色/换模。
4. 固定单位于未来，动态单在其前、后、以及两个固定单之间插入的成功与失败场景。
5. `固定单 -> 异常 -> 动态单` 与 `动态单 -> 异常 -> 固定单`，颜色和 Setup 不得丢失。
6. 同模具跨设备互斥；设备可用但模具被占用时必须延后。
7. 禁止深色到浅色的场景必须未排或选择其他合法位置，不能生成非法顺序。
8. 一个贪心顺序漏排、ejection chain 后全覆盖的回归样例。
9. 多次运行同一输入，排程结果、状态和目标值完全一致。
10. 随机属性测试：所有 `IsFeasible=true` 结果均通过独立校验器。

## 13. 性能预算与监控

目标范围：500 动态工单、平均 3 个 Alternative、50 台设备、500 个固定/异常占用，在 3 秒启发式预算内完成首轮构造。

记录并监控：

- 动态工单数、Alternative 数、固定单数、异常窗口数及合并后窗口数。
- 候选枚举次数、平均候选数、修复次数、修复成功率、未排数。
- 构造耗时、修复耗时、校验耗时、总耗时。
- 启发式完整率、作为 CP-SAT Hint 后的求解耗时改善比例。

当达到总时间预算时，停止修复，执行校验并返回受控的不完整诊断结果；不得无限计算或返回未验证计划。

## 14. 发布验收

上线前要求：

1. 第 12 节测试全部自动化通过。
2. 使用真实历史数据进行影子运行，与人工/MES 计划比对固定单、异常和换模处理。
3. 启发式完整且校验通过的结果才可提供给 CP-SAT 作为 Hint。
4. 自动下发开关默认关闭；先只读运行并观测完整率、校验失败率和耗时。
5. 任意校验失败、固定单冲突、超时或未排工单都必须阻止自动下发，并输出可追溯诊断。
